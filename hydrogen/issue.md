  ### 3. Critical Weaknesses & Risks to Address

  1. The "Join Key" Problem (Contract 2 → Findings):
      • In §6.3, the doc notes that Contract 2 provides a list of evidence and a separate list of disparities,
      but no foreign key connecting a specific element barrier (e.g. TOUCH_TARGET_TOO_SMALL) to a specific
      profile disparity (e.g. motor_impaired).
      • Hydrogen's fallback is: "all disadvantaged groups in the bundle for CRITICAL findings."
      • Risk: A low-contrast text issue might falsely get tagged as affecting motor_impaired, while a touch-
      target size issue might get tagged as affecting screen_reader_users. Dev 2 must provide a
      profile/barrier mapping tag, or Hydrogen needs a rule-to-constraint taxonomy lookup table.
  2. Silent Failure on Empty Disparities:
      • In §6.2, if disparities is empty, the score defaults to 100. If Dev 1 or Dev 2 fails to produce data
      or errors out, reporting a 100 ("perfect fairness") is misleading. It should return
      overall_fairness_score = None or raise a validation error.
  3. Repo Layout Divergence:
      • dev.md:91 defines Dev 3's directories as src/api/, src/llm/, and src/orchestrator/.
      • sub-arch.md introduces top-level root element folders (hydrogen/, helium/, lithium/, beryllium/).
      • Make sure your team either updates dev.md to adopt this scheme or nests them under src/ (src/hydrogen/,
      etc.) so imports and paths don't clash.

  # Hydrogen — Mathematical Engine
  
  **Status:** Revised draft for review
  
  ## 1. Purpose
  
  Hydrogen is the first CoHERence module (periodic-table naming, Z=1). It is Dev 3’s **deterministic fairness layer**. Its purpose is to transform Dev 2’s measured evidence and group-level disparity outcomes into:
  
  * a deterministic fairness score,
  * a breakdown explaining the score,
  * and ranked findings that identify the most important observed issues.
  
  Hydrogen does not call an LLM.
  
  Hydrogen is intentionally separated from the LLM analysis layer. The mathematical engine determines **what the measured outcomes are**, while the later Helium module determines **what those outcomes may mean and how they might be addressed**. This preserves reproducibility and prevents an LLM from directly controlling the numerical fairness score.
  
  The original architecture already establishes Hydrogen as the only component responsible for calculating `overall_fairness_score`, with the score derived from Contract 2 evidence and disparities. This separation remains unchanged.
  
  ## 2. What Hydrogen Is and Is Not
  
  ### 2.1 Hydrogen is
  
  Hydrogen is:
  
  * the only place where `overall_fairness_score` is calculated;
  * the deterministic layer that creates and ranks findings from Dev 2 evidence;
  * responsible for normalizing and validating disparity inputs before scoring;
  * responsible for identifying the worst observed group-level outcome;
  * a pure, deterministic function of its input contract;
  * reproducible: identical input produces identical output.
  
  ### 2.2 Hydrogen is not
  
  Hydrogen is not:
  
  * Dev 2’s WCAG, contrast, touch-target, typography, geometry, or other rule engine;
  * responsible for collecting browser interaction data;
  * responsible for calculating raw UI measurements;
  * responsible for generating persona stereotypes;
  * an LLM;
  * responsible for diagnosis;
  * responsible for remediation recommendations;
  * responsible for deciding that observed disparity constitutes intentional discrimination.
  
  Hydrogen should **not infer causation**. It reports measured disparity and evidence. Causal interpretation remains the responsibility of the later analyst layer.
  
  ## 3. Public Call Surface
  
  The public Hydrogen interface remains:
  
  1. `hydrogen.parse_contract2`
  2. `hydrogen.score_fairness`
  3. `hydrogen.rank_findings`
  4. `hydrogen.evaluate`
  
  The main entry point is:
  
  `hydrogen.evaluate`
  
  It receives an `EvidenceBundle` and a `report_id`, calculates the deterministic fairness score, ranks the findings, and returns a `HydrogenReport`.
  
  The score generated by Hydrogen must remain immutable downstream. Helium may add diagnosis and remediation text, but must not recalculate or modify the score.
  
  ## 4. Input Model
  
  ### 4.1 EvidenceBundle
  
  Hydrogen receives:
  
  * `evidence`
  * `disparities`
  * `target_url`
  * `profiles_tested`
  
  The original contract remains the authoritative source for these fields.
  
  ### 4.2 EvidenceRecord
  
  An evidence record contains information such as:
  
  * `element_selector`
  * `bounding_box`
  * `rule_id`
  * `severity`
  * `metric_value`
  * `recommended_min`
  
  Hydrogen does not independently verify these measurements. Dev 2 is responsible for generating them.
  
  ### 4.3 Disparity
  
  A disparity contains:
  
  * `metric`
  * `baseline_value`
  * `constrained_value`
  * `disparity_ratio`
  * `disadvantaged_group`
  
  However, Hydrogen must explicitly require the disparity ratio to have a **defined direction**.
  
  The contract must establish that:
  
  > `disparity_ratio > 1` always means that the constrained/disadvantaged group experienced a worse outcome than the baseline.
  
  This normalization is important because different metrics naturally have different directions.
  
  For example:
  
  * higher completion rate is better;
  * lower task time is better;
  * lower error count is better;
  * lower interaction cost is better.
  
  Dev 2 must therefore normalize each metric before it reaches Hydrogen.
  
  Hydrogen should never assume that a raw `constrained_value / baseline_value` calculation automatically represents disadvantage.
  
  ## 5. Disparity Normalization
  
  Before scoring, each disparity must pass validation.
  
  For every disparity:
  
  1. verify that the metric is recognized;
  2. verify that baseline and constrained values are valid;
  3. verify that the disparity ratio exists;
  4. verify that the ratio is finite and greater than zero;
  5. verify that the direction has been normalized so that values greater than `1.0` represent worse outcomes;
  6. reject or skip malformed values.
  
  A valid disparity therefore has the semantic interpretation:
  
  ```text
  1.0 = equal outcome
  >1.0 = worse outcome for constrained group
  <1.0 = constrained group performed better
  ```
  
  For scoring purposes, values below `1.0` should not generate a negative penalty.
  
  ## 6. Metric Semantics
  
  A major limitation of treating every disparity ratio identically is that different metrics have different meanings.
  
  For example:
  
  ```text
  4× task completion disparity
  ```
  
  is considerably more consequential than:
  
  ```text
  4× interaction-count disparity
  ```
  
  Therefore, Hydrogen should maintain a deterministic metric classification.
  
  A possible classification is:
  
  ### High-impact outcome metrics
  
  Examples:
  
  * task completion rate;
  * task failure rate;
  * abandonment;
  * critical interaction failure.
  
  ### Medium-impact behavioral metrics
  
  Examples:
  
  * task completion time;
  * error count;
  * recovery attempts;
  * backtracking.
  
  ### Lower-impact interaction-cost metrics
  
  Examples:
  
  * number of clicks;
  * number of navigation steps;
  * interaction distance;
  * redundant actions.
  
  The exact categories and weights should be validated against the CoHERence specification before implementation.
  
  The important architectural rule is that **metric semantics must be explicit rather than assuming that all ratios are equivalent**.
  
  ## 7. Per-Disparity Equity
  
  The proposed mathematical curve remains a useful starting point:
  
  ```text
  ratio = disparity_ratio
  
  equity_i =
      100 / (1 + k × max(ratio - 1, 0))
  ```
  
  where:
  
  ```text
  k = hydrogen.RATIO_STEEPNESS
  ```
  
  The proposed initial value remains:
  
  ```text
  RATIO_STEEPNESS = 0.20
  ```
  
  This produces approximately:
  
  | Disparity ratio | Equity |
  | --------------: | -----: |
  |            1.0× |    100 |
  |            2.0× |     83 |
  |            4.0× |   62.5 |
  |            6.0× |     50 |
  |           11.0× |     33 |
  
  This curve should initially be treated as a **versioned scoring policy**, rather than as an objective universal definition of fairness.
  
  Its purpose is to provide a transparent and tunable transformation from measured disparity to a 0–100 equity value.
  
  ## 8. Metric-Aware Scoring
  
  If metric weights are introduced, the weighting must remain deterministic.
  
  A disparity's contribution should therefore be conceptually:
  
  ```text
  metric disparity
          ↓
  normalized ratio
          ↓
  equity transformation
          ↓
  metric semantic weighting
  ```
  
  The exact weighting policy should be documented as named constants.
  
  For example:
  
  ```text
  COMPLETION_WEIGHT
  FAILURE_WEIGHT
  TIME_WEIGHT
  ERROR_WEIGHT
  INTERACTION_COST_WEIGHT
  ```
  
  These values must not be generated by the LLM.
  
  The LLM may explain why a disparity matters, but it must not decide the numerical weight at runtime.
  
  ## 9. Worst-Group Aggregation
  
  Hydrogen should continue to use a worst-group principle rather than a simple average.
  
  The rationale is that an average can hide severe exclusion.
  
  For example:
  
  ```text
  Group A = 100
  Group B = 100
  Group C = 20
  ```
  
  An average would produce approximately:
  
  ```text
  73.3
  ```
  
  while a worst-group calculation produces:
  
  ```text
  20
  ```
  
  For an inclusivity-testing system whose purpose is to identify who the software fails, the second representation is more informative.
  
  Therefore:
  
  ```text
  overall_fairness_score =
      worst observed equity
  ```
  
  should remain the default aggregation policy.
  
  The report should explicitly identify:
  
  * the worst-performing group;
  * the metric responsible for the bottleneck;
  * the disparity ratio;
  * the resulting equity score.
  
  The score should therefore be understood as a **worst-group outcome-equity score**, rather than a claim that every aspect of the software's fairness has been reduced to a single mathematically objective quantity.
  
  ## 10. Empty Disparity Handling
  
  The original proposal returns:
  
  ```text
  overall_fairness_score = 100
  ```
  
  when no disparity rows are available.
  
  This should be changed.
  
  No observed disparities does **not necessarily mean that the software is perfectly fair**. It may mean that:
  
  * no constrained profiles were tested;
  * the tasks did not expose a disparity;
  * the dataset was insufficient;
  * the measurement pipeline failed;
  * or disparity data was simply missing.
  
  Therefore, an empty disparity set should preferably be represented as:
  
  ```text
  score = null
  status = "INSUFFICIENT_EVIDENCE"
  ```
  
  or an equivalent explicit state.
  
  If the external Contract 3 schema absolutely requires an integer score, then `100` should not silently mean "perfect fairness." A separate field should distinguish:
  
  ```text
  score = 100
  confidence/status = insufficient_evidence
  ```
  
  The exact choice must be confirmed with the downstream contract.
  
  ## 11. Finding Ranking
  
  Finding ranking remains separate from score calculation.
  
  Hydrogen should rank findings using deterministic rules such as:
  
  1. severity;
  2. relationship to the worst-performing group;
  3. evidence strength;
  4. original evidence order as a deterministic tie-break.
  
  The severity ordering remains:
  
  ```text
  CRITICAL < WARNING < INFO
  ```
  
  where lower ranking value means higher priority.
  
  Importantly, finding severity must not automatically alter the fairness score unless that relationship is explicitly defined as part of the scoring policy.
  
  This preserves the original distinction:
  
  > **The score measures observed outcome disparity; findings identify potential technical contributors.**
  
  ## 12. Evidence-to-Profile Attribution
  
  The current temporary rule that assigns all disadvantaged groups to a CRITICAL finding should not be used as a final architecture.
  
  Without a reliable relationship between a finding and the profile that experienced the disparity, assigning every disadvantaged group creates false attribution.
  
  For example:
  
  ```text
  Finding:
  TOUCH_TARGET_TOO_SMALL
  
  Observed disparities:
  
  motor_impaired = 4.0×
  low_vision     = 1.1×
  keyboard_only  = 1.0×
  ```
  
  It is not valid to automatically state that the touch-target issue affected all three groups.
  
  Therefore, Hydrogen should require a future Dev 2 evidence-to-disparity join key.
  
  A finding should eventually contain enough information to establish:
  
  ```text
  finding
      ↓
  rule/evidence
      ↓
  affected interaction/task
      ↓
  affected profile/group
      ↓
  observed disparity
  ```
  
  Until that join exists, Hydrogen should mark the attribution as unresolved rather than asserting an unsupported relationship.
  
  Possible representation:
  
  ```text
  affected_profiles = []
  attribution_status = "UNRESOLVED"
  ```
  
  This is preferable to producing a confident but unsupported claim.
  
  ## 13. Separation Between Score and Diagnosis
  
  Hydrogen must not generate:
  
  * `diagnosis`;
  * `remediation_diff`;
  * causal claims;
  * intentional discrimination claims.
  
  These fields remain empty when Hydrogen produces the initial report.
  
  Helium subsequently receives the Hydrogen report and can populate the explanatory fields.
  
  However, Helium must not modify:
  
  ```text
  overall_fairness_score
  ```
  
  The score is owned exclusively by Hydrogen.
  
  This creates the following conceptual separation:
  
  ```text
  Hydrogen:
  "What happened mathematically?"
  
  Helium:
  "What might explain what happened?"
  ```
  
  This separation also reduces the risk of LLM hallucination affecting the numerical result.
  
  ## 14. Revised Hydrogen Pipeline
  
  The revised conceptual flow is:
  
  ```text
  Dev 2 Contract 2
         ↓
  parse_contract2
         ↓
  Validate / normalize disparity semantics
         ↓
  EvidenceBundle
         ↓
  ┌─────────────────────────────┐
  │ Deterministic calculations  │
  │                             │
  │ - validate ratios           │
  │ - normalize direction       │
  │ - calculate equity          │
  │ - apply metric semantics    │
  │ - identify worst group      │
  └──────────────┬──────────────┘
                 ↓
         score_fairness
                 ↓
        FairnessBreakdown
                 │
                 ├───────────────┐
                 ↓               ↓
        rank_findings       score result
                 │               │
                 └───────┬───────┘
                         ↓
                hydrogen.evaluate
                         ↓
                  HydrogenReport
                         ↓
                 helium.diagnose
                         ↓
                   Final Report
  ```
  
  ## 15. Revised FairnessBreakdown
  
  The existing fields should remain, with additional metadata where necessary:
  
  ```text
  overall_fairness_score
  outcome_equity
  bottleneck_metric
  bottleneck_group
  max_disparity_ratio
  skipped_metrics
  score_status
  ```
  
  Potential `score_status` values include:
  
  ```text
  VALID
  INSUFFICIENT_EVIDENCE
  PARTIAL
  ```
  
  This allows the system to distinguish a genuine high score from a high score produced under inadequate evidence.
  
  ## 16. Worked Example
  
  Consider:
  
  ```text
  Evidence:
  
  rule_id:
  TOUCH_TARGET_TOO_SMALL
  
  element:
  button#submit-order
  
  measured size:
  24×22px
  
  recommended minimum:
  48×48px
  ```
  
  And:
  
  ```text
  Disparity:
  
  metric:
  task_completion_rate
  
  baseline:
  1.0
  
  constrained:
  0.25
  
  disparity:
  4.0×
  
  group:
  motor_impaired
  ```
  
  Hydrogen calculates:
  
  ```text
  equity =
  100 / (1 + 0.20 × (4 - 1))
  
  = 62.5
  ```
  
  Therefore:
  
  ```text
  overall_fairness_score = 62
  ```
  
  Hydrogen can report:
  
  ```text
  bottleneck_metric:
  task_completion_rate
  
  bottleneck_group:
  motor_impaired
  
  max_disparity_ratio:
  4.0×
  ```
  
  Hydrogen can also rank:
  
  ```text
  TOUCH_TARGET_TOO_SMALL
  ```
  
  as a CRITICAL finding.
  
  However, Hydrogen should not state:
  
  > "The small button caused the motor-impaired group's failure."
  
  Instead, the finding should remain evidence-based:
  
  > The motor-impaired group experienced a 4× task-completion disparity, while the tested interface also contains a touch target below the specified minimum.
  
  Helium can later evaluate whether the evidence supports a causal relationship.
  
  ## 17. Determinism and Reproducibility
  
  Hydrogen must remain completely deterministic.
  
  The following must produce identical results for identical input:
  
  ```text
  hydrogen.score_fairness(bundle)
  ```
  
  Hydrogen must not use:
  
  * LLM calls;
  * network requests;
  * random sampling;
  * browser state;
  * external API responses;
  * dynamically generated scoring weights.
  
  The mathematical policy should therefore be version-controlled.
  
  A future report should ideally record the scoring-policy version, for example:
  
  ```text
  scoring_policy:
  "hydrogen-v1"
  ```
  
  This makes historical reports reproducible even if the scoring formula is later changed.
  
  ## 18. Core Design Principles
  
  The revised Hydrogen architecture follows six principles:
  
  ### 18.1 Measure before interpreting
  
  Dev 2 measures the interface and user outcomes.
  
  Hydrogen mathematically compares those outcomes.
  
  Helium interprets them.
  
  ### 18.2 Worst groups must not disappear into averages
  
  The worst observed outcome remains visible.
  
  ### 18.3 Different metrics require explicit semantics
  
  A disparity ratio must be normalized before it is scored.
  
  ### 18.4 Evidence and outcomes remain separate
  
  Evidence identifies potential technical contributors.
  
  Disparities describe observed outcome differences.
  
  Hydrogen must not silently treat the former as proof of the latter.
  
  ### 18.5 Attribution requires evidence
  
  A finding should not be associated with a profile unless the pipeline has sufficient evidence to establish that relationship.
  
  ### 18.6 LLMs do not control the score
  
  The numerical score belongs exclusively to Hydrogen.
  
  ## 19. Final Architecture
  
  Hydrogen therefore becomes a deterministic mathematical layer with the following responsibilities:
  
  ```text
  Contract 2
     ↓
  Normalization
     ↓
  Disparity validation
     ↓
  Metric-aware equity calculation
     ↓
  Worst-group aggregation
     ↓
  FairnessBreakdown
     +
  Deterministic finding ranking
     ↓
  HydrogenReport
     ↓
  Helium
  ```
  
  The resulting separation is:
  
  ```text
  Dev 2
  Measurement + behavioral evidence
  
          ↓
  
  Hydrogen
  Mathematical outcome equity + finding ranking
  
          ↓
  
  Helium
  Diagnosis + interpretation + remediation
  
          ↓
  
  Final CoHERence Report
  ```
  
  Hydrogen should therefore remain **small, deterministic, explainable, and independently testable**. Its purpose is not to make the final judgment about discrimination. Its purpose is to ensure that whatever judgment is later made by the LLM is grounded in a reproducible mathematical representation of the observed evidence.
